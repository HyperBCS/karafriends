## native-linux-1

**`-z lazy` does nothing, so the app won't start with libpipewire older than 0.3.50 (Ubuntu 22.04)** (high, confirmed, build-ci) · `native/karafriends/build.rs:7`

**Summary.** build.rs passes -Wl,-z,lazy, but rustc's x86_64 default (full RELRO, no PLT) makes all 26 libpipewire imports R_X86_64_GLOB_DAT, which ld.so resolves when the module loads, even under RTLD_LAZY. With libpipewire < 0.3.50 (Ubuntu 22.04's 0.3.48, which the README says is supported), loading native/index.node fails with "undefined symbol: pw_stream_get_time_n", so the app never starts and linux.rs's PIPEWIRE_MIN fallback (linux.rs:31-35, 50-58) is dead code. Fix: compile every crate with -C relro-level=partial on Linux, by adding it to the existing repo-root .cargo/config.toml or setting RUSTFLAGS in the release job, plus a readelf JUMP_SLOT check in CI.

**Scenario.** Ubuntu 22.04 with its stock libpipewire-0.3-0 0.3.48 (installed by default, and listed in README:20). The user unzips the release built on ubuntu-24.04 (release.yaml says that build is meant to run on 22.04) and launches it. src/main/index.ts:2 imports native/index.node at startup, and the import fails with "undefined symbol: pw_stream_get_time_n". Electron shows a main-process error and the app never starts; src/preload/index.ts:2 would fail the same way. The PulseAudio fallback and its "PipeWire 0.3.48 is older than 0.3.50" status line are never reached.

**Suggested fix.** Build every crate, not just the cdylib link, with `-C relro-level=partial` on Linux. With partial RELRO rustc's needs_plt() is true, so cpal and pipewire-rs call through the PLT, and `-z lazy` then works. Put it in a repo-root .cargo/config.toml (`[target.x86_64-unknown-linux-gnu] rustflags = ["-C", "relro-level=partial"]`): cargo reads config from the working directory, and package.json runs `cargo build --manifest-path native/Cargo.toml` from the root, so native/.cargo would be ignored. Alternatively set RUSTFLAGS in build-native-*. Then add a CI guard to the Linux jobs: `readelf -rW native/index.node | grep -q 'JUMP_SLOT.*pw_stream_get_time_n'`, or the stub-library dlopen test above. Note that a missing libpipewire (DT_NEEDED) still stops the app at launch either way, as README:24 says.

**Verifier.** CONFIRMED: I reproduced this myself. `readelf -rW` on both native/target/release/libkarafriends.so and native/index.node shows all 26 pw_* imports as R_X86_64_GLOB_DAT; the only JUMP_SLOT relocations are libc/libgcc ones. readelf -d has no BIND_NOW, so `-z lazy` was applied, but it only defers PLT slots and there are none for pw__. I built a stub libpipewire-0.3.so.0 exporting the 25 other pw__ symbols the module imports, without pw_stream_get_time_n, and dlopen(RTLD_LAZY) of the real module (both builds) fails with "undefined symbol: pw_stream_get_time_n". With the 26th symbol added it loads (scratch: /tmp/claude-1000/-home-brandon-Documents-karafriends/76fa4dac-61da-4447-8fd7-5bfaae6912c0/scratchpad/review/verify-native-linux/). src/main/index.ts:2 and src/preload/index.ts:2 import the module at startup, so the app cannot launch with libpipewire older than 0.3.50. That covers Ubuntu 22.04 and its derivatives, which README:15/20 lists as supported. linux.rs:31-35 itself says 22.04 ships 0.3.48. release.yaml builds with `rustflags: ""`, so release zips have rustc's default full RELRO and the same relocations. One note on the suggested fix: build.yaml's setup-rust-toolchain keeps its default rustflags (-D warnings), so RUSTFLAGS is set in that CI job. A set RUSTFLAGS overrides `[target] rustflags` in the root .cargo/config.toml, so a config-file fix would not reach CI builds. The relro flag has to go into those jobs' rustflags, or into RUSTFLAGS in build-native-*. Otherwise a readelf guard in CI would test a different binary than the one users run. | CONFIRMED: Not refuted; reproduced against the real module.

Path: release-linux-x86_64 builds with setup-rust-toolchain `rustflags: ""`, so rustc defaults apply: full RELRO and no PLT. `readelf -rW` on both native/index.node and native/target/release/libkarafriends.so shows all 26 pw_* imports as R_X86_64_GLOB_DAT. They are GLOBAL, unversioned and not WEAK. There are only 7 JUMP_SLOT relocations, none of them pw_*. Neither file has RPATH or RUNPATH. glibc resolves GLOB_DAT when the module loads regardless of RTLD_LAZY, so `-z lazy` has nothing to defer. src/main/index.ts:2 imports native/index.node first thing, so the main process fails before linux.rs runs.

Repro (scratchpad/review/repro-native-linux-1): a stub libpipewire-0.3.so.0 exports the 25 other pw_* symbols. Loading the real native/index.node through node's process.dlopen (RTLD_LAZY, the path Electron's require takes) with LD_LIBRARY_PATH pointing at the stub gives "FAILED: .../native/index.node: undefined symbol: pw_stream_get_time_n". The release .so fails the same way. With the 26th symbol in the stub, the module loads and exports its 18 functions. The module's init only exports functions, so no audio device was opened.

The suggested fix holds. A minimal rustc 1.99.1 cdylib that calls pw_stream_get_time_n, linked with -Wl,-z,lazy, gets a GLOB_DAT relocation with default flags and fails dlopen against the 25-symbol stub. With -C relro-level=partial it gets JUMP_SLOT and loads.

Trigger is real: Ubuntu 22.04 (and Mint 21.x) ships libpipewire 0.3.48. The README explicitly says 22.04 is supported and lists libpipewire-0.3-0 for it, so DT_NEEDED is satisfied and the missing symbol is fatal. CI runs only on 24.04 (PipeWire 1.0), so nothing catches it. The result is that the app never starts on a documented platform, every launch, so critical stands (limited to Linux with PipeWire < 0.3.50; Debian 12 has 0.3.65 and is unaffected).

Corrections and caveats:

- A repo-root .cargo/config.toml already exists (with [env] CPAL_ASIO_DIR), so the rustflags entry goes into it.
- Cargo treats a RUSTFLAGS environment variable, even an empty one, as overriding config rustflags. If setup-rust-toolchain's `rustflags: ""` exports an empty RUSTFLAGS, the config entry would be ignored in the release job. Either set RUSTFLAGS in the job or rely on the readelf guard to catch it.
- The comments in build.rs:1-4 and linux.rs:31-33 claim lazy binding, which is wrong today.

**Severity set at synthesis.** Confirmed, but no released version is affected (0.2.0 hasn't shipped), and it only hits hosts with PipeWire < 0.3.50 (Ubuntu 22.04, Mint 21). It blocks the Linux release on those distros rather than breaking a common party setup today. Its duplicate build-ci-1 was already rated high. Still fix_now.

## native-linux-3

**The 128-sample default buffer is meant for PipeWire's real-time threads but also applies on PulseAudio, where nothing runs real-time** (medium, plausible, realtime-audio) · `native/karafriends-lib/src/linux.rs:23`

**Summary.** DEFAULT_BUFFER is justified only by PipeWire's real-time threads (linux.rs:19-22), yet linux_buffer() and buffer_size() apply it to every host (linux.rs:391, 397-404; lib.rs:108; mixer.rs:269-270). cpal's PulseAudio host never promotes its threads, so with BufferSize::Fixed(128) it asks the server for a 2×128-frame (5.3 ms) playback target with 128-frame requests, served by an ordinary-priority client thread. It also never reports RealtimeDenied, so the 'Not real-time' note in the format line (which README:47 promises) never appears.

**Scenario.** On a PulseAudio system (the fallback for any PipeWire below 0.3.50, Ubuntu 22.04's default), the host leaves Mic buffer at its default. The mic output stream asks PulseAudio for 5.3 ms of buffering. The Electron renderer is busy decoding video and drawing the WebGL pitch bars, so the non-RT pulse client thread is late to refill, and the mic output likely underruns and crackles. Settings shows 'PulseAudio, 48 kHz, 128 samples' with no hint that the threads aren't real-time or that a bigger buffer would help.

**Suggested fix.** Make the default depend on the host: 128 for PipeWire (and ALSA, which cpal promotes); for PulseAudio either BufferSize::Default or about 512. Report it in linux_audio().defaultBufferSize so Settings shows the true default. On PulseAudio, add 'Not real-time: PulseAudio streams run at normal priority' to the format line, so the README's advice applies.

**Verifier.** PLAUSIBLE: These parts are confirmed. linux_buffer() falls back to DEFAULT_BUFFER (128) whatever the host (lib.rs:108), and mixer.rs:269-270 applies it to the output too. cpal-0.18.2's pulseaudio host has no realtime/priority code; only alsa, pipewire, wasapi, jack and aaudio promote threads, and its stream threads are plain std::thread::spawn. So the PulseAudio host never reports RealtimeDenied, and the 'Not real-time' note README:47 promises never shows on PulseAudio. make_playback_buffer_attr with Fixed(128) asks for tlength = maxlength = 256 frames (5.3 ms), and make_record_buffer_attr sets record maxlength = 128 frames, both with adjust_latency. That is a tight target for a normal-priority client thread inside the Electron renderer. I could not confirm that it actually underruns, though: the PulseAudio server's own threads are real-time, the cpal thread is not starved on an idle multi-core machine, and the host can raise Mic buffer in Settings. The mechanism is real and audible crackle is likely but unproven, on the less common PulseAudio path.

## native-linux-4

**If PipeWire's registry doesn't answer, every output is listed as a mic, and picking one feeds the speakers back into the mic output** (low, plausible, bug) · `native/karafriends-lib/src/linux.rs:209`

**Summary.** When pipewire_classes() returns None (any setup step fails, or the 2 s timeout), is_pipewire_device keeps any input-capable device that has a driver. cpal lists every Audio/Sink as DeviceDirection::Duplex (input-capable), and sinks have a factory.name driver, so the mic list then contains every output too. Opening one sets STREAM_CAPTURE_SINK, which records what that output plays.

**Scenario.** During a PipeWire or WirePlumber restart, or under load, cpal's Host::new succeeds but the second registry query times out. Settings then lists 'Built-in Audio Analog Stereo (Linux)' twice, the source and the sink, which often share a description. The host picks the sink entry. The mic now records the monitor of the output the mic output plays into, with reverb, which is a digital feedback loop that howls through the PA.

**Suggested fix.** In the fallback for inputs, also require `description.direction() == cpal::DeviceDirection::Input`. cpal gives sources Input and sinks Duplex, so this drops the sinks; outputs need no change. Pass the wanted direction alongside `class`.

**Verifier.** PLAUSIBLE: The mechanism is real. cpal pipewire/device.rs init_devices maps Role::Sink to DeviceDirection::Duplex (supports_input is true) and sets driver from factory.name. pw-dump on this laptop shows every Audio/Sink with factory.name api.alsa.pcm.sink, and build_input_stream on a Sink sets STREAM_CAPTURE_SINK. So when pipewire_classes() returns None, linux.rs:209-211 keeps the sinks as mics. The scenario is narrow, though. cpal's own host init (same registry walk, same 2 s timeout, and it returns a partial list on timeout) has to succeed while the second query fails. A PipeWire/WirePlumber restart usually fails cpal's init too, and then the code falls back to PulseAudio. Also, InputDevice::open re-lists through _input_devices() at open time (lib.rs:457-466), so the sink is opened only if the registry query fails again at open or watchdog-retry time. Otherwise the saved key just isn't found. The devices keep distinct keys (node names), so only the labels can collide. A cheap direction check would fix it.

## native-linux-5

**Every list, open and status call rebuilds the PipeWire host and walks the registry again, on the display's JS thread** (low, confirmed, performance) · `native/karafriends-lib/src/linux.rs:41`

**Summary.** system_host() is called afresh by linux_audio(), _input_devices(), _output_devices() and Mixer::build(). Each call runs cpal's full PipeWire enumeration: a new context, every audio and stream node bound, and a 2 s guard thread. Listing calls then run pipewire_classes(), a second connection with its own registry walk and guard thread. All of it runs synchronously in the renderer that draws the TV.

**Scenario.** Opening Settings runs outputDevices() (host + registry), linuxAudio() (a host built only for a status line and a quantum range) and inputDevices() (host + registry): five PipeWire round trips, measured at about 5-10 ms each here, so a few dropped frames mid-song. While a mic is unplugged, the 2 s watchdog repeats a host plus registry walk for every retry. If PipeWire stalls, each step waits its 2 s timeout, and so does the PulseAudio fallback, which leaks a thread each time. The TV then freezes for seconds at every Settings open and every watchdog tick.

**Suggested fix.** Choose the host once per operation and pass it down: one host and one pipewire_classes() per Settings open, with linux_audio() taking the host the listing already built. Optionally cache the chosen HostId after PipeWire succeeds, so a down mic's watchdog doesn't redo the PulseAudio and ALSA fallbacks. That saves about 3 of the 5 round trips per Settings open and keeps the mic output and the mics on the same sound system.

**Verifier.** CONFIRMED: Confirmed. system_host() builds a fresh cpal PipeWire Host (init_devices binds every audio node behind a 2 s guard thread) on every call: linux_audio(), _input_devices(), _output_devices() and Mixer's default path all call it, and input_devices/output_devices add a second connection in pipewire_classes(). The native calls run synchronously in the renderer (preload contextBridge). Settings.tsx:479-489 calls outputDevices and linuxAudio on open, and refreshInputDevices makes the next inputDevices re-list. The cost is small, though. strace of the existing listing test binary shows 2 pipewire-0 connects per listing, and the input and output listing tests together (4 connections, debug build) finish in 10-20 ms. That is about 20-40 ms per Settings open, plus roughly 10-20 ms every 2 s while a mic is down (nativeAudio.ts WATCH_MS). The multi-second freezes need a stalled PipeWire, which is an edge case. Worth doing if this code is touched, but low.

## tests-unit-4

**Linux's 'only real mics' filters have no tests, and the device-listing tests pass on whatever is listed** (low, confirmed, test-gap) · `native/karafriends-lib/src/linux.rs:151`

**Summary.** input_devices, output_devices, is_pipewire_device and alsa_devices decide which PipeWire nodes and ALSA PCMs Settings offers as mics and outputs. They take cpal::Device, so no test reaches them. linux.rs's own tests cover only version_at_least, alsa_label, buffer_size and stream_config. The two tests that list devices (lib.rs:1351, :1370) wrap everything in `if let Ok` and only check the ' (Linux)' suffix of whatever comes back. On the CI runner, which has no sound server, the fallback ALSA host lists nothing that opens, so they assert nothing there.

**Scenario.** Say someone changes the media-class check (linux.rs:206-208), for example to accept 'Stream/Input/Audio', which lists karafriends' own streams and other programs' recordings as mics again. Or they change alsa_devices' by-name rule (:309-327) so cards listed only by number drop out. Every Rust test still passes, and the regression the last Linux round fixed ('only real mics') comes back unnoticed.

**Suggested fix.** Split the decisions into pure functions over strings, for example `keep_pipewire(node: &str, classes: Option<&HashMap<String, String>>, class: &str, has_driver: bool) -> bool` and `alsa_kept(nodes: &[&str], prefixes: &[&str]) -> Vec<bool>`. The device functions then just map devices to strings and call them. Test them with node names taken from this laptop: input_default; an alsa_input.usb-… Audio/Source; an alsa_output….monitor; a Stream/Input/Audio node; plughw:CARD=PCH,DEV=0 against plughw:CARD=0,DEV=0. That is about 30 lines of tests.

**Verifier.** CONFIRMED: Every fact checks out. input_devices, output_devices, is_pipewire_device and alsa_devices (linux.rs:151-213, 308-329) take cpal::Device or cpal::Host, and nothing calls them in tests. linux.rs's test module (426-499) covers only version_at_least, alsa_label, buffer_size and stream_config. test_output_device_names and test_input_device_ids_and_labels (lib.rs:1350-1385) sit inside `if let Ok` and check only the name suffix, so the media-class rule (Audio/Source or Audio/Duplex, not Stream/*), the .monitor filter and the by-name/by-number ALSA rule can regress without any test failing. This logic was just fixed in the 'only real mics' round, so pure-function extraction plus regression tests is worth doing, at low priority.
